### Design Rationale

**No anti-patterns detected.** The microservice boundaries are well-justified:

1. **`AbstractActionBean`** is correctly shared across all 3 services — it's a pure infrastructure base class providing Stripes framework integration, with no business logic or domain specificity.

2. **`CatalogService`** is shared because:
   - `AccountActionBean` calls it to retrieve products for the user's favorite category after login/registration
   - `CartActionBean` calls it to fetch item details and check stock availability
   - In a real microservice architecture, these would become API calls to the Catalog service

3. **`ItemMapper`** and **`Item`** are shared because the `Item` entity bridges catalog data (product details) with cart/order operations (inventory management) — `OrderService` directly updates inventory through `ItemMapper`.

4. **`Account`** is shared into Shopping Cart & Order Management because `Order.initOrder()` takes an `Account` parameter to initialize shipping/billing address data.
